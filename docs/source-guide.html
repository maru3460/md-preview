全体像 — 見立てを 1 つ持つ

Rust は難しい、と聞いたことがあるだろう。所有権、ライフタイム、借用チェッカ。 4,000 行と聞けば、なおさら手が止まる。

ところが、このリポジトリの Rust を数えてみると様子が違う。 async/await は 1 箇所も出てこない。トレイト（インターフェース）の自作もゼロ。 ライフタイム注釈 <'a> が現れるのは、パーサと差分まわりの 3 ファイルだけだ。 つまり「怖い Rust」はほぼ使われていない。読むのに必要な文法は 10 項目に収まる。

Rust
約 4,100 行
10 ファイル。半分近くが request.rs と html.rs
自前 JS
約 4,300 行
12 ファイル。同梱ライブラリ（*.min.js）は除く
外部クレート
4 + 3 個
wry / tao / pulldown-cmark / notify（+ macOS 連携の objc2 系 3 個）
覚える文法
10 項目
async・自作トレイトはゼロ。ライフタイムは読み飛ばせる

文法より先に、アプリの見立てを 1 つ持ってほしい。 md-preview は「使い捨てのローカル Web サーバと、それ専用のブラウザ窓を、 1 個のバイナリに詰めたもの」である。

  • Rust 側 = サーバ。URL を受け取って HTML や JSON を返す（Express のルーティングに相当する部分が request.rs）
  • JS 側 = 普通のフロントエンド。fetch して innerHTML に入れる、見慣れた SPA

普通の Web 開発と違うのは 2 点だけ。通信が HTTP ではなく mdpreview:// という自前スキーム（カスタムプロトコル）であることと、 サーバとブラウザが同じプロセスの中にいることだ。 この見立てがあれば、Web 開発の知識がそのまま通用する。

通信路は図1 の 3 本ですべてである。①がデータの取得（Markdown の描画結果・ツリーの JSON・画像）、 ②が JS からウィンドウや OS への依頼（閉じる・Finder で表示など）、 ③が Rust から JS への唯一の割り込み（ファイルが変わったから再取得しろ）。 コードを読んでいて迷子になったら、いま見ている処理がこの 3 本のどれに乗っているかを考えるとよい。

読む順番

エントリポイントの main.rs から読み始めたくなるが、そこはウィンドウ管理という 「Rust 的に一番ノイズの多い場所」なので後回しにしたほうがよい。次の順を勧める。

  1. cli.rs — テーマ一覧を組み立てるだけの純粋な文字列処理。GUI 無関係で、Rust の見た目に慣れる肩慣らしに丁度いい
  2. request.rs — ViewKind → render_file → parse_route → handle_request の順。これがアプリの心臓部で、ここが読めれば残りは枝葉
  3. app_config.rs — 起動時にモードがどう決まるか
  4. main.rs — 配線。図1 の 3 本の通信路がコード上のどこかを確認する
  5. html.rs — Markdown がどう HTML になるか（pulldown-cmark のイベント変換）
  6. JS 側 — common.js → keymap.js → folder.js の順（→ JS 側の歩き方）
  7. 興味に応じて — embed.rs / diff.rs / theme.rs / platform.rs
このコードベース最大のナビはコメント

このリポジトリのコメントは「何をしているか」ではなく「なぜそうしたか・そうしないと何が壊れるか」を書いている。 関数の頭のコメントを読んでから中身を読むと、理解の速度がまるで違う。 さらに大きな判断の経緯は docs/（security-model.md など）に残っている。 文法で詰まる前に、まずコメントを信じて読むこと。

起動から表示まで

md README.md と打ってから窓が出るまでに何が起きるか。 まず知っておくべき意外な仕様がある。どのモードで開くかは、パスの「場所」で決まる。

起動のしかた モード 初期画面
md <ディレクトリ> folder ファイルツリー + 空のプレビュー
md <cwd 内のファイル> folder cwd をルートにしたツリー + そのファイル
md <cwd 外のファイル> single そのファイル 1 枚（親ディレクトリを監視）
cat x.md | md stdin パイプの中身 1 枚。ファイルが無いので監視なし

この分岐を書いているのが app_config.rs の AppConfig::from_path である。 モードが決まったあとの流れを時系列で追うと、こうなる。

  1. main() が引数から --detach 系を先に抜き取る
  2. run_terminal_command — --help / md theme / --html ならウィンドウを開かずここで終了
  3. 端末以外から起動されていたら detach_self で自分を別プロセスとして再起動し、親は即終了（呼び出し元のエージェントがタイムアウトで窓を巻き込まないため）
  4. テーマとユーザー CSS を読み、AppConfig::from_path がモードと初期 HTML を決める
  5. spawn_watcher がファイル監視を開始
  6. ウィンドウを作る。ただし非表示のまま
  7. WebView を構築 — 起動グローバル（MD_APPEARANCE など）+ モード別スクリプト（init.js / folder.js）を注入し、カスタムプロトコルと IPC ハンドラを配線する
  8. JS が動き出す。folder モードなら /?dir= を fetch してツリーを描く
  9. 描画が済んだ JS が ipc.postMessage('ready') を送る
  10. Rust が Ready イベントを受けて、ここで初めて window.set_visible(true)

6 と 10 が対になっているのがミソだ。窓を最初から見せると、描画が済むまでの一瞬、 真っ白なページがチラつく。だから「JS が描き終わったと自己申告するまで隠しておく」。 通信路②（IPC）が存在する理由の半分はこの 1 往復のためにある。

以降の動きは 2 つだけ。ユーザーの操作は通信路①（fetch）で完結し、 ファイルの保存は 監視スレッド → Reload イベント → 通信路③（evaluate_script）→ JS の MdReload() が該当ファイルなら再 fetch、という一方通行で流れる。

Rust を読むための最小文法

ここからが本題である。方針は 1 つ — 書けるようになる必要はない。読めればいい。 例はすべてこのリポジトリの実コードから引いているので、覚えた瞬間から使える。 JS が読めるなら「JS でいうと何か」で覚えるのが最短だ。

1. 関数・変数・式 — fn と let

fn message_html(msg: &str) -> String {
    crate::request::notice_html(msg)
}
src/diff.rs
  • fn 名前(引数: 型) -> 戻り値の型。型が後置になる以外は JS の関数と同じ
  • 最後の式が戻り値。セミコロンも return も付けない行が関数の末尾にあったら、それが返る値。return は途中で抜けるときだけ使う
  • let は JS の const に近い（既定で再代入不可）。変えたい変数だけ let mut と書く
  • 型は書かなくても推論される。let title = "stdin".to_string(); のように省略が普通

if も式なので、値を返せる。三項演算子の代わりにこう書く。

let marker = if is_active { "*" } else { " " };
src/cli.rs

2. Option・match・enum — このコードの読解の武器

Rust に null は無い。「無いかもしれない値」は Option という箱に入る。 中身があれば Some(値)、なければ None。 

pub struct RequestContext {
    // 単一ファイルモードで開いているファイル。フォルダモードでは None。
    pub single_file: Option<PathBuf>,
}
src/request.rs

取り出すときに多用されるのが let-else。「Some なら中身を取り出す。 None なら else 側で関数を抜ける」という早期リターンの型で、 request.rs のいたる所に出てくる。 

fn serve_view(ctx: &RequestContext, target: &Target, mode: ViewMode) -> Response {
    let Some((path, rel)) = resolve(target, ctx) else { return not_found_response() };
    let Some(r) = render_file(&path, &rel, mode) else { return not_found_response() };
    respond_fragment(target, r.body_class, r.html)
}
src/request.rs

enum は JS の文字列 union より強力で、選択肢ごとに違うデータを持てる。 このアプリの設計はほぼ enum でできている。 

/// ファイルの見せ方。この 4 択が唯一の分類。
pub enum ViewKind { Markdown, HtmlPage, Source, Binary }

/// 操作対象のファイルの指し方。
enum Target {
    Single,        // 単一ファイルモードで開いているファイル
    Rel(String),   // root 相対パス（String のデータ付き！）
}
src/request.rs

enum を分岐するのが match。switch に似ているが決定的な違いが 1 つある — 全部の場合を書かないとコンパイルが通らない。 だから読む側は「match を見れば、起こりうる状態が漏れなく列挙されている」と信じてよい。 enum の定義と match の分岐を往復するのが、このコードのいちばん確実な読み方だ。 

match classify_ext(&file_path) {
    ViewKind::Markdown => { /* ページとして描画 */ }
    ViewKind::HtmlPage => { /* style-gate を注入して返す */ }
    _ => { /* それ以外はバイト配信（_ は default 相当） */ }
}
src/request.rs handle_asset

3. Result と ? — 失敗したら即リターン

失敗しうる処理は Result（成功 Ok / 失敗 Err）を返す。 例外と throw は無い。そして末尾の ? は「失敗（Err や None）なら、 その場でこの関数からそれを返して抜ける」という演算子だ。 

pub fn write_active_name(name: &str) -> std::io::Result<()> {
    let dir = config_dir()
        .ok_or_else(|| std::io::Error::new(std::io::ErrorKind::NotFound, "HOME not set"))?;
    std::fs::create_dir_all(&dir)?;   // 失敗したらここで Err を返して終わり
    std::fs::write(dir.join("active-theme"), name)
}
src/theme.rs

Option を返す関数の中では ? は「None なら None を返す」になる。 file_path.file_name()?.to_str()? のような連鎖は 「途中のどこかが無ければ全体も無し」と読めばいい。

4. & と所有権 — 冒頭で棚上げした話

いよいよ & である。Rust では値に持ち主が 1 人だけいて、 関数に値をそのまま渡すと持ち主ごと移る（ムーブ）。渡した側はもう使えない。 それでは不便なので「貸すだけ」の記法があり、それが &（参照・借用）だ。

  • fn classify_ext(path: &Path) — 「Path を借りて読むだけ。もらいはしない」
  • .clone() — コピーを作って渡す。「貸し借りの揉め事を金で解決」する書き方で、このコードにも頻出する。読む側は深く考えなくてよい

型が 2 種類ずつあるのも同じ理屈だ。所有する型と、借りる型のペアになっている。

所有する型（実体を持つ） 借りる型（読み取りビュー） 中身
String &str 文字列
PathBuf &Path ファイルパス
Vec<u8> &[u8] バイト列

使い分けの目安は単純で、struct のフィールドや戻り値には所有型、関数の引数には借用型。 to_string() / to_path_buf() / to_vec() は全部「借り物を自分の所有物にコピーする」変換だ。 読むだけなら、所有権の理解はここまでで 9 割足りる。

5. struct と impl — クラスの分解版

pub struct RequestContext {
    pub root_dir: PathBuf,
    pub index_html: Vec<u8>,
    pub theme_css: String,
    pub custom_css: String,
    pub single_file: Option<PathBuf>,
}

impl RequestContext {
    fn single(&self) -> Option<&Path> {
        self.single_file.as_deref()
    }
}
src/request.rs

struct がデータ定義、impl がメソッド定義。クラスを 2 つに割っただけと思えばよい。 &self は JS の this に相当し、「自分を借りて読む」の意。 AppConfig::from_path(...) のような 型名::関数 は static メソッド呼び出しである。

6. メソッドチェーン — and_then / map / collect

このコードで一番よく見る「Rust らしい行」はこれだろう。 

let ext = path
    .extension()                        // Option<&OsStr>  拡張子（無いかも）
    .and_then(|e| e.to_str())           // Option<&str>    UTF-8 じゃないかも
    .map(|e| e.to_ascii_lowercase());   // Option<String>  あれば小文字化
src/request.rs

Option の上を Promise チェーンのように流れていると読めばいい。 途中のどこかで None になったら、以降は素通りして None のまま。 配列（イテレータ）でも同じ形が出る。 

let renderable = request::RENDERABLE_EXT
    .iter()
    .map(|e| json_string(e))
    .collect::<Vec<_>>()   // ここで初めて Vec に実体化（JS の Array.from 相当）
    .join(",");
src/app_config.rs

7. クロージャ・スレッド・Arc — main.rs のノイズの正体

|引数| 式 がクロージャで、JS の (x) => ... と同じ。 頭に move が付いたら「外の変数を借りずに、中へ取り込む」の意味で、 別スレッドに渡すときは必ずこれになる（貸したままスレッドに逃げられると持ち主が困るから）。 

let ctx = ctx.clone();               // Arc なので clone は「共有カウンタ +1」
std::thread::spawn(move || {
    responder.respond(handle_request(&ctx, &url_path, &query));
});
src/main.rs（カスタムプロトコルのハンドラ）

Arc は「複数スレッドから同時に読める共有の包み紙」。 リクエストごとにスレッドが立つので、設定一式（RequestContext）を Arc に包んで配っている。 main.rs が読みにくいのは大半がこの手のスレッド境界の作法で、 アプリのロジックとは関係がない。読み飛ばして関数名だけ拾えば流れは掴める。

8. マクロと生文字列 — ! が付くやつ

名前の後ろに ! が付いていたらマクロ（コンパイル時に展開される構文）。 使う分には関数と同じに見える。頻出は 4 つ。

マクロ JS でいうと 備考
format!("{}", x) テンプレート文字列 {} が穴。{name} の名前指定もある
println! / eprintln! console.log / console.error デバッグの友（→ 手を動かす）
matches!(x, パターン) [...].includes(x) の強化版 match を 1 行の bool にしたもの
include_str!("base.css") （相当なし） ビルド時にファイルを文字列定数として焼き込む

HTML 断片を作る場所では r#"..."# という書き方も頻出する。 これは生文字列で、中の " をエスケープせずに書ける。 r#"<p class="md-notice">"# のような行は、ただの文字列リテラルである。

include_str! の罠 — JS を直したのに反映されない

CSS も JS もテーマも、全部 include_str! でバイナリに焼き込まれている （だから md は単体ファイルで動く）。つまり src/*.js を編集しても、 cargo build し直して再起動するまで画面には反映されない。 「直したのに変わらない」と思ったら、まずこれを疑うこと。

9. 属性とモジュール — #[...] と mod

#[...] は次の項目への注釈。よく出るのは 3 つで、C の #ifdef の感覚で読める。

  • #[cfg(target_os = "macos")] — macOS ビルドのときだけ存在するコード（platform.rs はほぼ全部これ）
  • #[cfg(debug_assertions)] — デバッグビルド限定。md --html がリリース版に無いのはこれ
  • #[test] — テスト関数。各ファイル末尾の mod tests の中に住んでいる

モジュールは「lib.rs が目次」と覚える。pub mod request; と書かれていたら src/request.rs がツリーに登録され、他所から crate::request::render_file （crate:: = パッケージのルートから）で呼べる。 use は import、pub は export に相当する。

10. 読み飛ばしてよいもの

ここまでの 9 項目に入らない記号に出会ったら、たいてい次のどれかで、読み飛ばして支障がない。

  • <'a> — ライフタイム注釈。「この借り物はいつまで有効か」のメモで、 出てくるのは html.rs（LineIndex）・diff.rs（LineOp）・request.rs（Route）の 3 箇所だけ。 'a を消して読んでも意味は変わらない
  • <T> や impl Iterator<...> — ジェネリクス。「型は何でもいい」の印
  • spawn_watcher の戻り値のようなゴツい型 — 外部クレートの型をそのまま書いているだけ。関数名とコメントで意図は分かる

リクエストの一生

アプリを Web アプリと見立てたのだから、次の疑問は「ルーティングはどこか」だろう。 答えは request.rs の parse_route で、サイドバーのファイルをクリックしてから 本文が差し替わるまでは、図2 の 1 本道になっている。

③の safe_join はこのアプリのセキュリティの要で、 .. による親ディレクトリ参照と、正規化後に root の外へ出るパス（シンボリックリンク経由を含む）を拒否する。 「なぜ二段構えなのか」は関数のコメントと docs/security-model.md に書いてある。

JS 側の歩き方

JS は読めるという前提で、地図だけ渡す。モジュールは 12 個あるが、 構造を握っているのは 3 つのハブで、残りはそこにぶら下がる利用者にすぎない。

  1. MdKeymap（keymap.js） — ショートカットの単一定義元。 キー・説明・効く文脈・ハンドラ名が 1 つの表（BINDS）にあり、 唯一の keydown リスナがそこからディスパッチする。ヘルプ（?）の一覧も同じ表から出る。 キーの挙動を追うときは、各モジュールを探さずまずこの表を見る
  2. MdCommon.registerOverlay（common.js） — 検索バー・ヘルプ・⌘P・右クリックメニュー・ コメント入力の登録簿。「開いている間は素キーを止める」「Esc は最前面の 1 つだけ閉じる」を一括で捌く
  3. MdCommon.hydrate（common.js） — 本文を innerHTML で差し替えた後の後処理 （ハイライト・コピーボタン・図・目次・検索の再配線）。差し替える経路はどれも最後にこれを呼ぶ

Rust から渡ってくる値は window.MD_* のグローバル 4 つ （MD_APPEARANCE / MD_MENU_MODE / MD_FILE_REL / MD_RENDERABLE_EXT）。 定義元は app_config.rs の page_globals で、 起動スクリプトとして注入されるためページの CSP の対象外になる — 本文（信頼できない Markdown）の inline script は CSP で殺しつつ、自前の JS だけ動かす仕掛けの一部だ。 詳細は docs/security-model.md にある。

変更したいとき、どこを触るか

読めるようになった次は、直したくなる。よくある変更と入口の対応表を置いておく （設計の経緯は docs/refactor-review.md が詳しい）。

やりたいこと 触る場所
新しい表示対象を足す（画像 / .csv / .ipynb …） request.rs の ViewKind と render_file。拡張子表は RENDERABLE_EXT
エンドポイントを足す request.rs の Route と parse_route
本文差し替え後の後処理を足す common.js の hydrate()
表示モードを足す（blame / プレゼン …） viewmode.js の SPECS + keymap.js に view-<id> の行
ショートカットを足す・変える keymap.js の BINDS（表示と実処理の両方がここから出る）
オーバーレイ UI を足す MdCommon.registerOverlay() で登録するだけ
ページに JS モジュールを足す html.rs の PAGE_SCRIPTS に 1 行
起動モードの設定を変える app_config.rs
端末サブコマンドを足す cli.rs + main.rs の run_terminal_command

手を動かして確かめる

読むだけでは掴めない部分は、動かして壊して確かめるのが早い。開発の基本サイクルはこれだけだ。 

cargo run -- src/sample.md      # デバッグビルドして単一ファイル表示
cargo run -- .                  # フォルダモード（ツリー・⌘P・[ ] を試す）
cargo run -- --html src/sample.md > /tmp/out.html
                                # ウィンドウ無しで描画結果を確認（デバッグビルド限定）

cargo test                      # Rust テスト一式（スナップショット含む）
UPDATE_SNAPSHOTS=1 cargo test --test render
                                # 描画を意図して変えたときの期待値更新（差分は目で確認）
npx playwright test             # UI テスト（初回は npm install と npx playwright install webkit）

デバッグの小技を 3 つ。

  • Rust 側は eprintln! を挟んで cargo run。 GUI アプリだが、端末から起動すれば前景に残るので stderr がそのまま見える
  • JS 側を触ったら必ず cargo build（include_str! の罠）。 UI の挙動確認は Playwright テストの土台になっている cargo run --example serve -- . 7878 で普通のブラウザから開くのも手
  • rust-analyzer（VS Code 拡張ほか）を入れると、省略された型が全部インレイ表示され、 定義ジャンプも効く。Rust 未経験の読解ではこれが一番効く投資
安全網はすでにある

描画の構造を壊すと tests/render.rs のスナップショットが、 キーボードやオーバーレイの挙動を壊すと tests/ui/smoke.spec.js が落ちる。 「試しに変えてみて、テストに叱られて理解する」が、このリポジトリでは安全にできる。

用語集

クレート / Cargo
クレート = Rust のパッケージ（npm のパッケージ相当）。Cargo はそのビルド & パッケージ管理ツールで、Cargo.toml が package.json に当たる。
WebView / WKWebView
OS 同梱のブラウザエンジンを自分の窓に埋め込む部品。macOS では Safari と同じ WebKit（WKWebView）。Chromium を同梱する Electron と違い、バイナリが小さい。
wry / tao
このアプリの土台クレート。tao がウィンドウとイベントループ、wry がその中の WebView を担当する（Tauri プロジェクト製）。
カスタムプロトコル
http:// の代わりに登録する自前スキーム（ここでは mdpreview://）。WebView からのリクエストがサーバではなく自プロセスの関数（handle_request）に届く。
IPC
プロセス間通信……の名を借りた、JS → Rust の一方向メッセージ（window.ipc.postMessage）。ここでは close / ready / 右クリックメニューの 3 用途だけ。
イベントループ
「イベントが来るまで寝て、来たら 1 つ処理する」無限ループ。GUI アプリの心臓。main.rs の event_loop.run がそれで、閉じる・表示・リロードの 3 イベントだけ捌く。
pulldown-cmark
Markdown パーサのクレート。文書を「イベントの列」（見出し開始・テキスト・終了…）として流してくる。html.rs はこの列を横取りして加工している。
CSP と nonce
Content-Security-Policy。ページ内でどの script の実行を許すかの宣言。本文（信頼できない Markdown）由来の script は拒否し、正しい nonce（使い捨てトークン）付きの自前 script だけ許す。
所有権 / 借用
値には持ち主が 1 人、というRust の中核ルール。渡すと移り（ムーブ）、& を付けると貸すだけ（借用）。GC 無しでメモリ安全を実現する仕組みだが、読むだけなら「& は借り物マーク」で足りる。
スナップショットテスト
出力（ここでは描画 HTML）を丸ごとファイルに保存しておき、次回以降の出力と突き合わせるテスト。意図しない変化を「差分」として検出する。
